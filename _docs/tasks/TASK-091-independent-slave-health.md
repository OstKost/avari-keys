# TASK-091 — Независимые проверки Slave с Master

Целевой релиз — **v1.12.1** (предложение).

## Цель и границы

Master проверяет каждый Slave от своего имени. Отказ канала к одной ноде не меняет статусы остальных и не задерживает публикацию их результатов. Доступность Slave API, состояние VPN-служб и публичная доступность показываются отдельно.

После v1.12.0 Master потерял доступ к S1 по служебному туннелю. Проверки S3 и S4 тоже шли через него, хотя по прямому маршруту оба API отвечали. S2 исключён из внедрения и сохраняет статус блокировки. SBOX вне VPN-кластера.

## Порядок работ

1. **Маршруты.** Для каждого Slave описать основной путь с Master и, при необходимости, независимый резервный. Для S3 и S4 проверить прямой HTTPS из процесса Master с обычной проверкой сертификата и штатной авторизацией. Устранить их зависимость от туннеля S1 на уровне маршрутизации служебного трафика. Для S1 подтвердить отдельный защищённый путь, работоспособный при отказе текущего туннеля. Сохранить частный доступ к служебным портам и `X-API-Key`. Адреса и настройки окружения хранить в приватном инвентаре.
2. **Мониторинг.** В `internal/monitor` и `internal/client` выполнять проверки параллельно, с отдельным бюджетом времени на каждую ноду. При сетевых сбоях пробовать настроенный резервный путь этой же ноды в пределах бюджета. Ошибки TLS и авторизации отображать отдельно. Публиковать результат ноды сразу после проверки, независимо от телеметрии, публичных проб и каскадной диагностики. Повтор изменяющих запросов после неоднозначного тайм-аута требует отдельной гарантии идемпотентности.
3. **Уведомления.** В `internal/telegram` вынести отправку из цикла мониторинга в ограниченную очередь с тайм-аутами и объединением повторов. Убирать токены и ключи из ошибок до записи в журнал. Перевыпуск ранее раскрытого токена провести отдельно через приватную конфигурацию.
4. **Панель и диагностика.** В `internal/master`, `internal/models` и SPA показывать время последней проверки и понятную причину. Предусмотреть состояния «API доступен», «Доступен через резерв», «API недоступен» и «Нет свежих данных». Сохранить отдельное отображение блокировки, качества VPN-служб и публичной доступности.

## API и данные

- Расширить текущие ответы списка и диагностики нод совместимыми полями для состояния Slave API, категории причины, времени проверки и признака резервного пути. Действующие поля сохранить для старых клиентов.
- Основной адрес брать из существующей настройки ноды. Резервный задавать опционально с обратной совместимостью. В пользовательские ответы передавать категорию причины и вид пути без служебных адресов и секретов.
- Синхронно обновить типы, `client.ts` и `mockClient.ts`. Справочники — [бэкенд](../architecture/BACKEND_STRUCTURE.md) и [SPA](../architecture/FRONTEND_SPA.md).
