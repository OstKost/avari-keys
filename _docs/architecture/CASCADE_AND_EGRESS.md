# Двухкаскадное туннелирование, Egress-шлюзы и Watchdog

## 1. Концепция двухкаскадного туннеля (Double-Hop)

Двухкаскадная архитектура разработана для обхода жестких ТСПУ/DPI-блокировок зарубежных протоколов:

```
[Клиент в РФ]
      │  (AmneziaWG с DPI-обфускацией: Jc, Jmin, Jmax, S1, S2, H1-H4)
      ▼
[M0 Ingress (Москва, РФ)]
      │  (Внутренний WireGuard туннель awg1 / awg3)
      ▼
[S1/S4 Egress (Нидерланды / Германия)]
      │  (NAT / Прямой выход в свободный интернет)
      ▼
[Целевой зарубежный ресурс]
```

### Преимущества:
1. **Для операторов связи РФ**: Клиент обменивается замаскированным трафиком только с сервером внутри РФ (M0), трансграничный VPN-трафик отсутствует.
2. **Для внешнего интернета**: Запросы приходят с чистого IP-адреса дата-центра в Европе (Нидерланды/Германия).
3. **Бесшовность для клиента**: При падении или смене Egress-сервера клиентский ключ, конфигурация и IP-адрес внутри туннеля **не меняются**.

## 2. Кворум-проверки доступности Egress (`internal/egress/`)

Выходной шлюз проверяется контроллером через мультипроверку с независимым кворумом (5 целей):
1. **Google / Multi-IP** (через fallback-провайдеров: `api.ipify.org`, `icanhazip.com`, `ipinfo.io`, `api.myip.com`).
2. **Cloudflare** (`1.1.1.1`).
3. **Telegram API** (`api.telegram.org`).
4. **OpenAI / ChatGPT** (`chatgpt.com`).
5. **Meta / Grok** (`x.ai` / `meta.com`).

**Правило кворума**: Шлюз считается здоровым (`online`), если минимум **3 из 5** проверок завершились успешно. Для обхода перехвата DNS в РФ используется DoH-резолвинг.

## 3. Механизм переключения шлюза (Egress Switching)

Переключение (ручное или автоматическое) выполняется атомарно через `egress.Manager`:
1. **Pre-flight**: Проверка доступности интернета через целевой резервный интерфейс (например, `awg3`). Если он недоступен, переключение отменяется.
2. **Transaction**: Смена маршрута по умолчанию в таблице маршрутизации Linux.
3. **Post-flight**: Контрольная проверка прохождения трафика через новый шлюз.
4. **Rollback**: Если после переключения внешний интернет недоступен, маршрут автоматически откатывается на исходный интерфейс (`Recover`).

---

## 4. Автоматическое переключение (Auto-Failover)

- Включается индивидуально для каскадной ноды (`auto_failover_enabled = true`).
- Приоритет резервных шлюзов задается в `failover_priority` (например, `["awg1", "awg3", "awg4"]`).
- **Защита от флаппинга (Cooldown)**: После переключения шлюза активируется кулдаун (по умолчанию 10 минут), в течение которого авто-переключения блокируются.
- При срабатывании Auto-Failover администраторам отправляется алерт в Telegram-бот с указанием причины и нового шлюза.

## 5. Сторожевой таймер (Watchdog) и перезапуск в 1 клик (TASK-080)

### Проблема «зависших» сессий WireGuard:
Иногда соединение WireGuard переходит в полуоткрытое состояние (stalled): сервер M0 отправляет пакеты (`TX > 50 KB`), но ответы не приходят (`RX == 0`). При этом интерфейс формально поднят, но трафик не идет.

### Решение Watchdog:
1. **Автодетектирование**: Воркер `monitor.HealthChecker` анализирует дампы интерфейсов `awg dump`. Если обнаружено состояние `TX > 50KB && RX == 0`, флаг `IsFrozen` помечается как `true`.
2. **Автоматический перезапуск**: При зафиксированном зависании HealthChecker вызывает `slaveCli.RestartCascadeEgress(ctx, iface)`.
3. **Точечный перезапуск**: Выполняется команда `systemctl restart awg-quick@awgX`, что перезапускает исключительно зависший Egress-туннель, **не затрагивая** входящий пользовательский интерфейс `awg0` и соседние соединения.
4. **Кнопка в веб-интерфейсе**: На странице диагностики сервера ([`ServerDetailPage.tsx`](file:///Volumes/KingstonM2/Projects/avari-keys-mvp/apps/frontend/src/components/ServerDetailPage.tsx)) доступна кнопка **«Перезапуск»**, позволяющая администратору мгновенно перезагрузить туннель в 1 клик.
